## The in-process ledger and the Fabric deployment

`pledge/ledger/network.py` reproduces the protocol logic in one process
(k-of-n endorsement, BFT ordering with 2f+1 quorum certificates, re-validation
at commit, key issuance only from the service's own committed block) and lets
any node misbehave (`silent`, `equivocate`, `endorse_all`, `bad_share`,
`rogue`). It does not model network delay, so the ledger latencies and
throughputs in the paper come from the Fabric deployment in `fabric/`. The Go
chaincode re-implements every check of `pledge/ledger/chaincode.py`; the
cross-language test vectors (`fabric/pkg/pledgecc/testdata/vectors.json`,
generated by `scripts/gen_vectors.py`) make sure both accept and reject exactly
the same transactions.
